# RCA — Build failure (run 9bf14d36-a38a-4ba0-a222-4880d2e3c9cb)

## Deployment
- Deployment: `github-integration-27` (app: **"PantryKart Live"**)
- Template in use: `fastapi_react_mongo_shadcn_base_image` (farm) / frontend_type=cloudflare
- Failed step: `build_image` (Cloud Build, `frontend-build` stage, step 13/14)

## Symptom (verbatim from build log)
```
[RETRY] Attempt 1 of 3: yarn install --prefer-offline --check-files --network-timeout 100000
yarn install v1.22.22
info No lockfile found.
...
success Saved lockfile. Done in 0.03s.
yarn run v1.22.22
error Couldn't find a package.json file in "/app"
```
The farm Dockerfile does `COPY frontend/ /app/` then `yarn install && yarn build`. `yarn install` completes in 0.03s (nothing to install) and `yarn build` fails because there is **no `package.json` in `frontend/`**.

## Root cause — TEMPLATE / ARCHITECTURE MISMATCH (not a manifest bug)
This app is a **Google AI Studio export** (Vite + React 19 + Express + Supabase + Gemini). Its real code lives at the **repo root**, not in the farm layout the template expects. Verified in the eph sandbox from the run's pulled source:

- `frontend/` contains **only `.env`** — no `package.json`, no source. → this is what breaks the build.
- The actual frontend + server are at **root**: `package.json` (`"name": "react-example"`, `"type": "module"`), `vite.config.ts`, `index.html`, `src/` (App.tsx, main.tsx…), `server/` (businessLogic.ts, store.ts, supabase.ts), `server.ts`, `server.js`, `tsconfig.json`, `bun.lock`, `package-lock.json`.
- Root `package.json` scripts: `build: "vite build && esbuild server.ts --bundle --platform=node --format=cjs --outfile=dist/server.cjs"`, `start: "node server.js"`, `main: server.js`. It is a **single Node/Express process** serving on `PORT` (default 3000).
- `backend/` contains **only** `requirements.txt` + `tests/` — there is **no `server.py`**. The app uses **Supabase**, not MongoDB.
- `etc/supervisor/conf.d/supervisord.conf` is the stock farm scaffold: `[program:backend] command=uvicorn server:app ... directory=/app/backend` and `[program:frontend] command=yarn start directory=/app/frontend` — both point at directories that don't contain the app.

So the app was scaffolded as a farm app but the real application (a Node/Vite/Express/Supabase/Gemini "PantryKart Live" build) was dropped at the root without being restructured into the farm layout.

## Why this is NOT fixable by a deployment-manifest edit
Even if the frontend `COPY` path were patched, the farm template still cannot run this app:
1. **Runtime has no Node.** The farm final/runtime base image is Python-based (nginx + uvicorn); it does not ship a Node runtime, so `node server.js` cannot start in production. (node in the eph sandbox is a sandbox-only addition and is NOT evidence about the deployed image.)
2. **No FastAPI backend exists** — `uvicorn server:app` in `/app/backend` has no `server.py` to import, so the backend process and the `/health` check would fail.
3. **No MongoDB** — the app uses Supabase; the farm mongo provisioning/migration path is irrelevant.

Re-authoring the entire manifest set to build and run a Node/Express app on a non-Node base image is out of scope for a manifest break-fix and would not converge.

## Recommended fix (owned by E1 / user — not the deployer agent)
Pick ONE:
- **A. Deploy on a Node-compatible template.** This app is a single Node/Express server (`node server.js`, port 3000) + Vite static build + Supabase — it does not fit `fastapi_react_mongo`. Re-create the deployment with a template whose runtime has Node and serves `node server.js` directly (e.g. the Next.js/node family), with nginx/health pointed at port 3000.
- **B. Restructure the source to the farm contract.** Move the React/Vite frontend into `frontend/` (with its own `package.json`), implement a real FastAPI app at `backend/server.py` exposing `/health` and the API, and migrate data off Supabase to the managed Mongo. This is a substantial rewrite.

Option A is far less work and matches the app's actual stack.

## Secrets note
Frontend/root `.env` and `backend/.env` carry **Supabase** keys (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `VITE_*`). Whichever template is chosen, these must be wired as deployment secrets for the Node server at runtime.

## Evidence source
Reproduced from the run's pulled source in an eph sandbox (`/app/scratch`): confirmed `frontend/` has no `package.json`, the app is a root-level Vite/Express/Supabase build, and `backend/` has no `server.py`. The build failure is fully explained by the structure; no manifest change was attempted.
