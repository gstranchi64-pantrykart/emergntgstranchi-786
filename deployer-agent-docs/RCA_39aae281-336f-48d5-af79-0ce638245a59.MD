# RCA — Deploy build failure (run 39aae281-336f-48d5-af79-0ce638245a59)

App: **PantryKart Live** (`github-integration-27`) · Template: `fastapi_react_mongo_shadcn_base_image` (FARM) · frontend_type: cloudflare

## Symptom
Build fails at the `frontend-build` stage (step #38, 13/14):
```
[RETRY] Attempt 1 of 3: yarn install --prefer-offline --check-files --network-timeout 100000
yarn install v1.22.22
info No lockfile found.
...
success Saved lockfile.  Done in 0.03s.
yarn run v1.22.22
error Couldn't find a package.json file in "/app"
```
The farm Dockerfile does `COPY frontend/ /app/` then `yarn install && yarn build` in `/app`. `yarn install` runs against an empty dir (no package.json → trivial empty lockfile), then `yarn build` aborts because there is no package.json. Both prior initial runs (9bf14d36, 0853c281) failed identically — this is deterministic, not transient.

## Root cause — the app does NOT match the FARM template it is being deployed with
Verified by inspecting the pulled source in an eph sandbox (`/app/scratch`):

1. **Frontend is at the repo ROOT, not in `/frontend`.**
   - Root contains the real app: `package.json`, `vite.config.ts`, `index.html`, `src/` (App.tsx, components, …), `bun.lock`, `package-lock.json`, `tsconfig.json`.
   - `/frontend/` contains ONLY a stray `.env` — no package.json, no src. That is why `COPY frontend/ /app/` + `yarn build` finds nothing.

2. **It is a Node/Express + Vite app (built with Bun), NOT FastAPI + React + Mongo.**
   - `package.json` name `react-example`, `"type":"module"`, `main: server.js`, engine node>=20.
   - `build` = `vite build && esbuild server.ts --bundle --platform=node --outfile=dist/server.cjs`; `start` = `node server.js`.
   - Runtime is a single **Express** server (`server.ts` → `dist/server.cjs`) listening on **port 3000**, serving the Vite build and `/api/*` itself.
   - Server logic in `server/` (businessLogic.ts, store.ts, supabase.ts, otpService.ts).

3. **`/backend/` has NO FastAPI app.** It contains only `requirements.txt` and `tests/test_audit_bill_flow.py` — there is no `server.py`. But supervisord (`etc/supervisor/conf.d/supervisord.conf`) defines `[program:backend] command=uvicorn server:app ... directory=/app/backend`, which the farm `entrypoint.sh` parses and runs. Even if the frontend built, the backend process would crash immediately (no `server` module), failing health_check.

4. **Data layer is Supabase, not Mongo.** The app uses `@supabase/supabase-js` and `server/supabase.ts`; its env (`SUPABASE_URL`, `SUPABASE_*_KEY`, `SUPABASE_PROJECT_REF`, `VITE_SUPABASE_*`, and a server-side Gemini key) is Supabase-based. The farm template provisions Emergent-managed Mongo (`MONGO_URL`/`DB_NAME`), which this app does not use.

## Why this is NOT a manifest fix (and why I did not re-run the pipeline)
Fixing only the frontend COPY path would still leave three blockers: (a) the farm runtime stage is the Python/uvicorn+nginx base image and runs `uvicorn server:app` — it cannot run a Node Express server and has no app to import; (b) the server listens on 3000, not the farm's 8001-behind-nginx contract; (c) the DB is external Supabase, not the provisioned Mongo. Rewriting both Dockerfile stages + entrypoint + nginx to run Node on a Python base with Supabase would be a full re-architecture of the deployment, not a diagnosed manifest defect — out of scope and unreliable. The failure is deterministic across 3 runs, so another `resume_pipeline` fails identically.

## Required fix (owned by E1 / user — source + template choice)
This app was generated as a Bun/Node/Vite/Express/Supabase app but committed to a FARM (FastAPI+React+Mongo) deployment. Reconcile one of two ways:

**Option A — deploy with a Node-appropriate template** (preferred; matches the app as-built). This single-process `node server.js` (Express serving Vite build + API on port 3000) does not fit any FastAPI/uvicorn farm/expo template. Choose a template/runtime that runs a Node server.

**Option B — re-scaffold the source to the FARM shape** (large rewrite): implement a real FastAPI `backend/server.py` (uvicorn on 8001) that re-creates the Express/Supabase API, move the React app into `/frontend/` with its own `package.json`, and migrate the data layer to the Emergent-managed Mongo the template provisions. Re-porting `server/businessLogic.ts` (~319KB) + `store.ts` to Python is substantial.

### Secrets note (after the structural decision)
Whichever path, the app needs `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_PROJECT_REF` (and the server-side Gemini API key) available as deployment secrets. These are app/Supabase-owned values — not something I can set. NOTE: the checked-in `.env` embeds live-looking Supabase anon + **service_role** keys; the service_role key is privileged and should be managed as a secret, not committed.
